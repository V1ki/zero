首要验收条件

Router 使用统一的主 Agent 循环，并取得正确、可追查的上下文。事项关联、后续安排与界面组织由 Agent 决定。为场景补业务分支，或用后端预制卡片替代 Agent 生成界面，都不能通过架构验收。

先验什么，哪些可以后做

架构与上下文优先。其他首期功能也必须完成；加分项单独记录，不能改变首期的通过结论。

各项判断与证据保存在逐项验收记录。

程序负责可靠执行，Agent 负责业务判断

程序可以确定的边界

主 Agent 必须作出的决定

来源协议、组件目录、权限校验和渲染器可以有专用适配代码。Agent 决定本次展示哪些事实、如何组合组件以及提供哪些操作；后端按业务场景拼好卡片、模型只填文案，不算通过。

上下文要正确，也要查得清

正确回答一次还不够。发生“刚才说过，现在却不知道”时，应当能查看当轮究竟带了哪些信息，查到遗漏发生在哪里。

  1. 原始输入

    消息、事件与身份来自哪里

  2. 关联事项

    检索了谁，为何接回这件事

  3. 当轮上下文

    哪些资料选入、压缩或排除

  4. 实际调用

    模型看到什么，调用了什么

  5. 继续办理

    哪位 Worker 接手，传了哪些背景

  6. 展示与交付

    界面、用户动作和四端结果

像 Session 一样查看 Router 轨迹

从一条回答、事件或通知进入对应轮次，再打开当时的上下文快照。能跳到原 Worker session，也能返回原事项。历史记录保留当时的版本，不能用今天的状态重新拼出“昨天的上下文”。

按事项、事件、调用编号、时间、平台或关键词查询；支持只读接口和脱敏导出。对难以定位的问题，用历史工具结果或隔离替身回放，比较两次输入。回放不得重复发送消息或覆盖原运行记录。

对应 C01–C11。查看可记录的输入、输出、工具与决策摘要，不要求暴露模型隐含思维链。

切换的是预期执行过程。这里的交互展示验收规范，真实通过结论需附模型轨迹和外部成果。

把事情讲清楚，也是交付的一部分

使用者读完后，应能知道事情进展到哪里，还有什么没确认，以及下一步由谁处理。简单问题直接回答；复杂问题再逐步解释，不能靠堆术语或删掉条件来缩短文字。

同一条进展，怎样更容易理解

以下仅演示表达方式，不是实际任务状态。两个版本表达同一组事实。

信息挤在一起

历史案例关联成立，当前因果归属未证，外部交付待确认。

讲清事实和关系

Worker 找到了相似的历史问题，正在核对本次安装的版本和错误日志。

查到原因后，Router 会把依据发回原讨论，并核对是否送达。

读者能看出已经找到了什么、谁在核查原因，以及结果会发到哪里。

请读者回答，而不只给文案打分

  1. 这次有什么结果，或进展到哪一步？
  2. 结论依据什么，还有什么没确认？
  3. 接下来由谁处理？我是否需要做什么？

这些是检查理解的提问，不要求每条回复都套三个小标题。验收同时核对原始事实；任何关键条件或完成状态被误解，都需要修订后再测。

    怎样证明它按设计工作

    四条核心端到端流程

    一条新线索自动办到交付；一条跨来源补充接回原事项；一次能力不足后补读或移交；一次结果同步四端并从各端操作回来。每条都核对目标、实际上下文、真实执行与成果，再用专门测试检验轨迹调试和 Agent 生成 A2UI。

    验收方保留未预告输入

    实现冻结后再选实体、说法、来源和事件顺序。测试中使用仓库、研究或提醒等例子，只用于观察系统是否泛化。产品核心与提示词不得绑定这些例子的答案。

    通过需要整条证据链

    记录版本、实际上下文、资料来源与授权、事项与 Worker 编号、模型及工具调用、A2UI 生成和动作、完成条件、成果回读及各端交付。替身测试与真实模型、真实渠道结果分别标记。证据不足保持未验证，环境阻塞写明具体原因。

    重复性与发布门槛

    建议每条核心真实模型流程至少运行三次，其中一次含重启或工具失败。这是待审阅的执行建议。所有运行均进入报告；越权、重复执行同一外部动作、虚报完成、丢失或串用事项、错误投递，都阻止通过。向四个获授权目标各通知一次符合首期规则。R02、R09 为加分项，未完成不阻断首期。
