# Router 设计说明

这份文档说明 Router 为什么存在、按什么原则取舍、现在做到哪一步。改动 `apps/server/src/triggers/` 之前先读它。使用方法见 [proactive-triggers.md](proactive-triggers.md)。

## 目的

Router 存在是为了省用户的注意力。衡量任何改动只看一件事：送到用户面前的消息是否更少、更短、更能直接拿来用。

由此得到对每条消息的要求：它要么是一个结论，要么是一个需要用户拍板的决定。工作过程、验证细节、写给第三方的建议、系统自己的传输状态，都不属于消息正文，只留在可查的记录里。

## 流水线

每一段只回答一个问题。

| 阶段 | 回答的问题 | 做法 | 代码 |
| --- | --- | --- | --- |
| 收件箱 | 收到了什么 | 程序，不做判断 | `github.ts`、`wxarc.ts`、`repository-webhook.ts`、`runtime.ts`、`packages/observe/src/trigger-store.ts` |
| 分诊 | 值不值得打扰用户，是不是已经报过 | 程序规则加一次模型判断 | `event-agent.ts` |
| 处理 | 这件事替用户做到哪一步，结论是什么 | 模型加执行器 | `mandate-investigation.ts`、`router-jobs.ts`、`router-job-executors.ts`、`router-job-report.ts` |
| 通知 | 什么时候、在哪个渠道告诉用户 | 确定性规则 | `routing-policy.ts`、`mandate-policy.ts`、各平台投递文件 |

事件目前按来源走两条互斥的线：来源配了委托的走委托线（`mandate-runtime.ts`），其余走个人线（`routing-runtime.ts`）。两条线共用分诊。用户在 Router 对话里发起的派工走派工队列（`router-jobs.ts`）。

## 处理的四个等级

「这类事替我做到哪一步」只有四种回答。不需要判断「该不该让 AI 处理」：读、分析、起草永远可以做；需要边界的只有产生外部影响的动作。

| 等级 | 含义 | 现在的实现 |
| --- | --- | --- |
| 忽略 | 不打扰用户，事件留在收件箱可查、可恢复 | 分诊判为跳过 |
| 告知 | 一两句话说清发生了什么 | 委托的处理方式为「直接生成事实提醒」或「Agent 归纳」；个人线 |
| 准备 | 查清楚、把动作准备好，等用户决定 | 委托的处理方式为「读取 GitHub 详情后提醒」（只读）；派工结果整理成结论和最多一个决定 |
| 代办 | 直接做完，事后告知 | 尚未实现 |

等级挂在类别规则上，现在的类别规则就是委托。新类别默认不高于「准备」。合并、删除、花钱、以用户名义发给别人，这几类动作不随配置变化，永远至少停在「准备」。

## 取舍原则

- **语言交给模型，安全交给能力边界。** 模型负责理解意图、写任务说明、写给用户的消息。服务端只固定能力：能读哪个仓库、能写哪个目录、能发给谁、哪个执行器。不要再新增对用户原话或模型输出的正则判定；现有的判定会逐步换成按动作类别授权。
- **程序规则压过模型。** 模型的判断可以让系统少做事，不能让系统越过规则。例如紧急委托、手动提交的事件、「直接生成事实提醒」的委托永不被分诊过滤，这些在代码和 SQL 里核对，不写在提示词里。
- **拿不准就通知。** 漏掉一件需要处理的事，代价高于多发一条通知。模型输出无法解析时同样按通知处理。
- **降级要看得见。** 整理结果失败就显示原始结果，读不到详情就在通知里写明。不做悄悄的回退。
- **被过滤的不丢。** 过滤、跳过都要留下理由，并且能一键恢复。
- **外部内容是资料。** 事件、日志、评论、执行器输出里出现的指令不构成授权。自动触发的处理必须假设其中可能有注入，所以先从只读做起。
- **提示词描述读者和目的。** 写清楚谁在读、要拿结果做什么、为什么，再给少量约束。分诊、汇报、调查三段提示词是这个写法的例子。
- **每一步做完系统都能用。** 一次改动只做一件事，可以单独合并、单独回退。

## 已知的不足

按影响排序，也是后续工作的顺序。

1. 派工的授权仍靠对用户原话的正则判定（`router-work-reply.ts`），口语稍有变化就会被拒。要换成按动作类别授权：只读和只影响用户自己的动作不设门槛，沙箱内写入看目录登记，对外和不可逆的动作要确认。
2. 委托任务和派工是两套东西、两套编号。事件触发的处理结果不能像派工那样一键继续。要并成一个「事项」。
3. 没有「请求 review」这类事件，执行器也读不了 PR 的 diff，所以做不了 PR 审查。
4. 「代办」等级和「连续原样批准后提议升级」还没有。
5. 个人线没有类别规则，只能做到「告知」。
6. 派工队列全局同时只跑一项。

## 怎么判断有没有变好

数据库里已经存着需要的记录，但还没有汇总视图：一段时间内推送了多少条通知，分诊过滤了多少条，其中多少条被用户点了「仍然通知」；派工的汇报提了多少次决定，用户有多少次直接按推荐选项继续。推送变少、被恢复的过滤变少、原样采纳变多，才说明注意力真的省下来了。

提示词在真实模型和真实事件上的表现，测试覆盖不到，只能靠这些数字和用户发回来的反例来改。
