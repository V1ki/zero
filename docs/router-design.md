# Router 设计说明

这份文档说明 Router 为什么存在、按什么原则取舍、现在做到哪一步。改动 `apps/server/src/triggers/` 之前先读它。使用方法见 [proactive-triggers.md](proactive-triggers.md)。

## 目的

Router 存在是为了省用户的注意力。衡量任何改动只看一件事：送到用户面前的消息是否更少、更短、更能直接拿来用。

由此得到对每条消息的要求：它要么是一个结论，要么是一个需要用户拍板的决定。工作过程、验证细节、写给第三方的建议、系统自己的传输状态，都不属于消息正文，只留在可查的记录里。

## 流水线

每一段只回答一个问题。

| 阶段 | 回答的问题 | 做法 | 代码 |
| --- | --- | --- | --- |
| 收件箱 | 收到了什么 | 程序，不做判断 | `github.ts`、`wxarc.ts`、`repository-webhook.ts`、`runtime.ts`、`packages/observe/src/trigger-store.ts` |
| 分诊 | 值不值得打扰用户，是不是已经报过 | 程序规则加一次模型判断 | `event-agent.ts` |
| 处理 | 这件事替用户做到哪一步，结论是什么 | 模型加执行器 | `mandate-investigation.ts`、`router-jobs.ts`、`router-job-executors.ts`、`router-job-report.ts` |
| 通知 | 什么时候、在哪个渠道告诉用户 | 确定性规则 | `routing-policy.ts`、`mandate-policy.ts`、各平台投递文件 |

事件目前按来源走两条互斥的线：来源配了委托的走委托线（`mandate-runtime.ts`），其余走个人线（`routing-runtime.ts`）。两条线共用分诊。用户在 Router 对话里发起的派工走派工队列（`router-jobs.ts`）。

任务和派工的关系：派工属于发起它的用户，按用户的派工范围编号（网页用户是 `general`），任务只是派工的一个可选归属。在 GitHub 任务的网页对话里发起的派工记下任务编号，回执留在任务对话，执行时服务端从任务读出名称、委托目的和最近几次命中摘要，作为引用的背景交给执行者。仓库只来自委托配置，任务标题和摘要来自外部事件，只作资料，不参与选仓库、选目录或确认写入。任务停止跟踪不会中止派工，派工能否执行仍只看它自己的授权；任务对话随之只读，后续操作回到主对话按编号进行。

## 处理的四个等级

「这类事替我做到哪一步」只有四种回答。不需要判断「该不该让 AI 处理」：读、分析、起草永远可以做；需要边界的只有产生外部影响的动作。

| 等级 | 含义 | 现在的实现 |
| --- | --- | --- |
| 忽略 | 不打扰用户，事件留在收件箱可查、可恢复 | 分诊判为跳过 |
| 告知 | 一两句话说清发生了什么 | 委托的处理方式为「直接生成事实提醒」或「Agent 归纳」；个人线 |
| 准备 | 查清楚、把动作准备好，等用户决定 | 委托的处理方式为「读取 GitHub 详情后提醒」（只读）；派工结果整理成结论和最多一个决定 |
| 代办 | 直接做完，事后告知 | 尚未实现 |

等级挂在类别规则上，现在的类别规则就是委托。新类别默认不高于「准备」。合并、删除、花钱、以用户名义发给别人，这几类动作不随配置变化，永远至少停在「准备」。

## 取舍原则

- **语言交给模型，安全交给能力边界。** 模型负责理解意图、写任务说明、写给用户的消息。服务端只固定能力：能读哪个仓库、能写哪个目录、能发给谁、哪个执行器。不要新增对用户原话或模型输出的正则判定。从原话里取出编号或仓库名属于解析，可以保留；判断用户想不想要某件事交给模型。
- **授权只来自用户本轮亲手写的话，按动作能造成的后果分级。** 只读的动作（ZeRo 分析、查询派工状态）改变不了任何东西，结果也只给同一位用户看，由 Router 模型自己决定，照常受身份、受众、GitHub 授权和队列的约束。能写的动作（Codex 开工和继续）不同：Router 模型读过历史、事件、工具结果和执行器汇报，其中任何一段都可能是别人写的，所以它想调用工具不足以让写入开始。服务端在任何状态产生之前，另做一次不带工具的模型调用，只给它用户本轮的原话和服务端写明的拟执行动作（新开还是继续、哪个仓库），让它判断原话本身是否在要求这件事。拿不准、出错、超时或输出无效，都不开工，并把原因告诉用户。Codex 的仓库同样只从原话、为当前入口登记的目录名或本对话最近一项派工里确定，不由模型挑：只读分析的仓库是模型选的，只有用户当时写明过它，才能成为后续修改的默认目标。用户原样回复汇报里印出的「继续派工 #N：选 K」，与点选项按钮一样，视为回答服务端自己提出的问题，不再确认。代码在 `router-write-check.ts` 和 `router-work-turn.ts`。
- **程序规则压过模型。** 模型的判断可以让系统少做事，不能让系统越过规则。例如紧急委托、手动提交的事件、「直接生成事实提醒」的委托永不被分诊过滤，这些在代码和 SQL 里核对，不写在提示词里。
- **拿不准就通知。** 漏掉一件需要处理的事，代价高于多发一条通知。模型输出无法解析时同样按通知处理。
- **降级要看得见。** 整理结果失败就显示原始结果，读不到详情就在通知里写明。不做悄悄的回退。
- **被过滤的不丢。** 过滤、跳过都要留下理由，并且能一键恢复。
- **外部内容是资料。** 事件、日志、评论、执行器输出里出现的指令不构成授权。自动触发的处理必须假设其中可能有注入，所以先从只读做起。
- **提示词描述读者和目的。** 写清楚谁在读、要拿结果做什么、为什么，再给少量约束。分诊、汇报、调查三段提示词是这个写法的例子。
- **每一步做完系统都能用。** 一次改动只做一件事，可以单独合并、单独回退。

## 模型调用的记录

Router 的 8 个模型调用点（分诊、Router 对话、委托草案、GitHub 调查、ZeRo 派工执行、派工汇报、写入确认、渠道任务追问）都经
`runTriggerModel`（`event-agent.ts`）进同一个 loop 基座，每次调用写一份自己的事件文件，格式与主会话相同，见
[session-event-log.md](session-event-log.md)「Router 的事件文件」。业务表仍只存结论和会话编号；文件里是模型实际看到的全文
（进入提示词之前已经过 `secretFilter`），包括 Router 对话从业务表拼出的历史，所以业务表正文清除后请求仍能还原。
事件文件遵守与业务表相同的正文保留期，见 [proactive-triggers.md](proactive-triggers.md)「数据、恢复与代码落点」。
Codex 派工的每次执行同样有一份事件文件，只记一次 `worker` 工具调用的开始和结果，不记 Codex 的中间过程。
每类调用记自己的 usage 用途（`router_triage`、`router_chat`、`router_commission`、`router_investigation`、`router_job`、
`router_job_report`、`router_write_check`、`router_task_followup`），日志经与主会话相同的结构化 logger 写进当天目录的 `run.log`。

## 已知的不足

按影响排序，也是后续工作的顺序。

1. 委托任务和派工仍是两套东西。GitHub 任务的网页对话已经可以派工：派工记在任务下（`router_job_steps.task_id`），仓库固定为委托跟踪的仓库，汇报和选项回到任务对话，编号仍与主对话共用一套。但事件触发的处理结果本身还不能像派工那样一键继续，任务的通知也不带派工结果，WXARC 任务和 IM 里的任务追问也不能派工。要并成一个「事项」。
2. 没有「请求 review」这类事件，执行器也读不了 PR 的 diff，所以做不了 PR 审查。
3. 「代办」等级和「连续原样批准后提议升级」还没有。
4. 个人线没有类别规则，只能做到「告知」。
5. 派工队列全局同时只跑一项。

## 怎么判断有没有变好

Router 工作台的「效果统计」按需从已有记录算出近 7 天或 30 天的数字，并与之前同样长的一段对比，不另存汇总（`router-summary-store.ts`）。每个数字回答一个问题：

- **送到的通知数**：注意力花在了哪里。只算网页提醒和平台已受理的 IM 投递，一个事件算一条，待核对、延后和失败的不算。
- **分诊过滤数，以及其中被用户点「仍然通知」或「仍然提醒」找回的数**：过滤是否太狠。找回的比例高，说明分诊挡掉了用户想看的。
- **「读取 GitHub 详情后提醒」的通知里，带「未能读取」或「调查未完成」说明的数**：调查有没有真正读到东西。读不到的多，多半是监听凭证的权限不够。
- **派工完成的执行数、整理成汇报的数、退回原始结果的数**：用户是否还在读原始结果。
- **汇报提出的决定数、用户回答的数、其中选了推荐项的数**：问题有没有问对。很少按推荐回答，说明汇报问错了问题，或推荐不对。

推送变少、被找回的过滤变少、原样采纳变多，才说明注意力真的省下来了。委托线的找回和用户所选的选项是这一版才开始记录的（`mandate_effects.triage_restored`、`router_job_steps.answered_option`，两个回答路径都写），统计会注明哪段时间早于记录开始；个人线的找回从保存的分诊结论补记（`trigger_routes.triage_restored`）。这些列只给统计读，不影响重试、分诊参考和按钮。

提示词在真实模型和真实事件上的表现，测试覆盖不到，只能靠这些数字和用户发回来的反例来改。
